📌 Принцип 1: Зачем нужно наследование? (Проблема дублирования)

🔍 Основная проблема

Представь: ты пишешь программу для автосалона. Тебе нужны классы для Машины, Велосипеда и Грузовика.

БЕЗ наследования ты пишешь так:

// ❌ ПЛОХО: дублирование кода
class Car {
    String brand;      // Одинаково во всех классах!
    int maxSpeed;
    double weight;
    int doors;
}

class Bike {
    String brand;      // Снова те же поля!
    int maxSpeed;
    double weight;
    boolean hasBasket;
}

class Truck {
    String brand;      // И снова!
    int maxSpeed;
    double weight;
    int cargoCapacity;
}

⚠️ Проблемы такого подхода:

  1. DRY нарушен — одно и то же написано 3 раза
  2. Сложно поддерживать — изменил поле? Правь в 3 местах!
  3. Нет общей логики — нельзя сделать массив «всех транспортных средств»

✅ Решение: вынести общее в базовый класс

Всё, что одинаково у всех транспортных средств → в класс Vehicle.

Всё, что уникально для каждого → в классы-наследники.

    ┌─────────────────────────────────────────┐
    │           🚗 Vehicle (Родитель)         │
    │  • brand (общее для всех)               │
    │  • maxSpeed (общее для всех)            │
    │  • weight (общее для всех)              │
    │  • move() (все едут, но по-разному)     │
    └─────────────────────────────────────────┘
         ↑           ↑           ↑
         │           │           │
    ┌────┘           │           └────┐
    │                │                │
    🚗 Car           🚲 Bike          🚚 Truck
    • doors          • hasBasket       • cargoCapacity
    • hasAC          • wheelSize       • axles

📌 Принцип 2: Как работает super() внутри памяти?

🔍 Что происходит при создании объекта?

Когда ты пишешь new Car(...), в памяти создаётся один объект, но он содержит:

    Память при: Car car = new Car("Toyota", 200, 1500, 4, true);

    ┌───────────────────────────────────────────┐
    │           Объект в памяти (Car)           │
    ├───────────────────────────────────────────┤
    │  Часть от Vehicle (родитель):             │
    │  ├─ brand: "Toyota"                       │
    │  ├─ maxSpeed: 200                         │
    │  └─ weight: 1500                          │
    ├───────────────────────────────────────────┤
    │  Часть от Car (наследник):                │
    │  ├─ doors: 4                              │
    │  └─ hasAC: true                           │
    └───────────────────────────────────────────┘

    👉 super(...) инициализирует ВЕРХНЮЮ часть!
    👉 this. инициализирует НИЖНЮЮ часть!

⚠️ Почему super() должен быть ПЕРВОЙ строкой?

Потому что нельзя использовать объект, пока он не инициализирован полностью.

Сначала фундамент (родитель), потом стены (наследник). Иначе — ошибка компиляции!

public class Car extends Vehicle {
    public Car(String brand, int maxSpeed, double weight,
               int doors, boolean hasAC) {

        // 👇 ПЕРВАЯ СТРОКА: инициализируем часть от Vehicle
        super(brand, maxSpeed, weight);

        // 👇 ВТОРАЯ+: инициализируем часть от Car
        this.doors = doors;
        this.hasAC = hasAC;
    }
}

📌 Принцип 3: Полиморфизм — как JVM выбирает метод?

🔍 Главный вопрос

У тебя есть:

Vehicle v = new Car(...);
v.move();  // ❓ Какой метод вызовется: Vehicle или Car?

Ответ: метод Car. Но почему?

✅ Динамическое связывание (Dynamic Binding)

  1. Компилятор (когда пишешь код) проверяет тип ссылки: Vehicle. Он говорит: «У Vehicle есть метод move() — ОК, код валиден».
  2. JVM (когда программа работает) смотрит на реальный объект в памяти: Car. Она говорит: «Это Car! Вызову версию move() из Car».
    ВРЕМЯ КОМПИЛЯЦИИ              ВРЕМЯ ВЫПОЛНЕНИЯ
    (Компилятор)                  (JVM)
    ↓                             ↓
    ┌─────────────────┐           ┌─────────────────┐
    │ Тип ссылки:     │           │ Реальный объект:│
    │ Vehicle         │           │ Car             │
    │                 │           │                 │
    │ Видит: move()   │           │ Вызывает:       │
    │ ✅ Есть метод   │           │ Car.move()      │
    └─────────────────┘           └─────────────────┘

⚠️ Важный нюанс!

Полиморфизм работает только для переопределённых методов.

Если у Car есть метод openTrunk(), которого нет у Vehicle — через ссылку Vehicle его не вызвать без casting!

📌 Принцип 4: Зачем нужен instanceof перед casting?

🔍 Проблема

У тебя есть массив Vehicle[]. Ты хочешь вызвать openTrunk(), но он есть только у Car.

Vehicle[] garage = {car, bike, truck};

for (Vehicle v : garage) {
    // ❌ БЕЗ instanceof — опасно!
    Car c = (Car) v;  // А если v — это Bike?!
    c.openTrunk();     // 💥 ClassCastException!
}

⚠️ Что происходит без instanceof?

  1. Компилятор пропускает код (он видит приведение типа).
  2. Программа запускается.
  3. Когда цикл доходит до Bike, JVM пытается привести Bike к Car.
  4. 💥 ClassCastException — программа «падает»!

✅ Безопасный подход

for (Vehicle v : garage) {
    // 👇 Сначала проверяем тип
    if (v instanceof Car) {
        // 👇 Только потом приводим
        Car c = (Car) v;
        c.openTrunk();  // ✅ Безопасно!
    }
}
    instanceof — это «вопрос» к JVM:

    ┌──────────────────────────────────────┐
    │  v instanceof Car?                   │
    │                                      │
    │  Если v = Car    → true  ✅          │
    │  Если v = Bike   → false ❌          │
    │  Если v = Truck  → false ❌          │
    └──────────────────────────────────────┘

    👉 Только если true — делаем casting!

📌 Принцип 5: Логические методы (boolean) — зачем они?

🔍 Концепция

Методы, которые возвращают boolean, не делают действий. Они отвечают на вопрос.

Метод Вопрос Логика
canCarryCargo() «Может ли везти груз?» Car: doors >= 4
Truck: cargoCapacity > 0
hasBasket() «Есть ли корзина?» Bike: возвращает поле hasBasket

✅ Зачем это нужно в тесте?

Ты можешь писать условную логику на основе возможностей объекта:

for (Vehicle v : garage) {
    if (v instanceof Car) {
        Car c = (Car) v;
        if (c.canCarryCargo()) {
            System.out.println("This car can carry cargo!");
        }
    }
}

📌 Принцип 6: Валидация в сеттерах (без throw)

🔍 Проблема

Пользователь может передать некорректные данные:

car.setMaxSpeed(-100);      // ❌ Отрицательная скорость?
car.setMaxSpeed(1000);      // ❌ Нереалистично!
car.setBrand(null);         // ❌ Пустая марка?

⚠️ Порядок проверки на null

НЕПРАВИЛЬНО:

if (brand.trim().isEmpty() || brand == null) {
    // 💥 Если brand = null, brand.trim() выбросит NullPointerException!
}

ПРАВИЛЬНО:

if (brand == null || brand.trim().isEmpty()) {
    // ✅ Сначала null, потом методы!
}

✅ Стратегия валидации (без throw)

  1. Проверь условие (например, скорость от 0 до 300).
  2. Если ОК — установи значение.
  3. Если НЕ ОК — установи значение по умолчанию (например, 100).
  4. Опционально: выведи предупреждение в консоль.

📌 Принцип 7: Проектирование иерархии — как принимать решения?

🔍 Вопрос на засыпку

Как решить, какие поля вынести в базовый класс, а какие оставить в наследниках?

✅ Тест «ВСЕ или НЕ ВСЕ»

Задай вопрос: «Это есть у ВСЕХ транспортных средств?»

Поле Есть у всех? Куда?
brand ✅ Да (Car, Bike, Truck) Vehicle
maxSpeed ✅ Да Vehicle
doors ❌ Нет (только у Car) Car
hasBasket ❌ Нет (только у Bike) Bike
cargoCapacity ❌ Нет (только у Truck) Truck

📌 Принцип 8: Частые ошибки и как их избежать

❌ Ошибка 💡 Почему неправильно ✅ Как правильно
super() не первой строкой Объект не инициализирован полностью Всегда первая строка конструктора
Забыть @Override Компилятор не проверит сигнатуру метода Всегда добавляй аннотацию
Casting без instanceof ClassCastException при выполнении Сначала проверка, потом приведение
brand.trim() до проверки на null NullPointerException Сначала brand == null
Поля private в базовом классе Наследники не видят их Используй protected
Сеттер назван isTrained() Конфликт с геттером для boolean Геттер: isTrained(), Сеттер: setTrained()

📌 Принцип 9: Как думать при написании кода?

❓ Вопрос 1: С чего начать?

Начни с базового класса (Vehicle). Определи:

  1. Какие поля общие для ВСЕХ?
  2. Какие методы будут у ВСЕХ?
  3. Какие методы будут переопределяться?
❓ Вопрос 2: Как проверить, что наследование правильное?

Примени тест «является»:

  • ✅ Car является Vehicle? Да → наследование ОК
  • ✅ Bike является Vehicle? Да → наследование ОК
  • ❌ Car является Bike? Нет → не должно быть наследования
❓ Вопрос 3: Когда использовать полиморфизм?

Когда хочешь обрабатывать разные типы одинаково:

// Хочешь вызвать showInfo() у всех транспортных средств?
Vehicle[] garage = {car, bike, truck};
for (Vehicle v : garage) {
    v.showInfo();  // Каждый покажет свою версию!
}
❓ Вопрос 4: Когда использовать casting?

Только когда нужно вызвать уникальный метод наследника:

// openTrunk() есть только у Car
if (v instanceof Car) {
    Car c = (Car) v;  // Casting
    c.openTrunk();     // Уникальный метод
}
